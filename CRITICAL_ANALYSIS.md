# Анализ критических рисков сервиса

Дата: 2026-02-15

## 1) Критический риск безопасности: статический JWT_SECRET
- В коде используется захардкоженный секрет `JWT_SECRET = "dev_secret_change_later"`.
- При утечке исходников или угадывании секрета злоумышленник может самостоятельно выпускать валидные JWT-токены и получать доступ с правами любых пользователей.
- Рекомендация: вынести секрет в переменные окружения, использовать длинный случайный ключ и ротацию.

## 2) Критический риск безопасности: path traversal при загрузке файлов (API)
- В API-обработчике `/tickets/{ticket_id}/attachments` имя файла собирается как `f"{timestamp}_{file.filename}"` и без нормализации записывается через `UPLOAD_DIR / safe_name`.
- Если в `file.filename` попадут сегменты вроде `../../...`, путь может выйти за пределы каталога `uploads`, что потенциально позволяет перезаписывать произвольные файлы на сервере.
- Рекомендация: использовать только безопасное имя (UUID + допустимое расширение), отбрасывать/очищать исходное имя, проверять что итоговый путь внутри `UPLOAD_DIR`.

## 3) Критический риск безопасности: cookie с токеном без secure и CSRF-защиты
- Для web-логина токен пишется в cookie (`httponly=True, samesite="lax"`), но без `secure=True`.
- Нет явной CSRF-защиты для state-changing web-form endpoint'ов.
- На HTTP и/или в смешанных сценариях это увеличивает риск перехвата/подмены и CSRF-атак.
- Рекомендация: ставить `secure=True` под HTTPS, добавить CSRF-токены для POST/PATCH/DELETE форм.

## 4) Критический риск надежности: отсутствие валидации входных FK (часть endpoint'ов)
- При создании/обновлении тикетов `project_id`/`executor_id` принимаются от клиента и не проверяются на существование сущностей до commit.
- При некорректных id возможны ошибки БД/500 в рантайме, что ломает сценарии пользователей.
- Рекомендация: валидировать связанные сущности заранее и возвращать 400/404 с понятной ошибкой.

## 5) Критический риск доступности: неограниченная загрузка файлов в память
- В web-обработчике загрузки используется `content = await file.read()` (чтение целиком в память), без ограничений размера.
- Большие файлы могут вызывать рост памяти и деградацию/падение процесса.
- Рекомендация: потоковая запись чанками, лимит размера файла и проверка типа/расширения.
